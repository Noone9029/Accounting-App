# Production deployment implementation

This directory prepares a new production environment. It does not promote the existing Vercel/Supabase burner, enable a provider, or establish launch readiness. The public application hostname is the proposed `app.ledgerbyte.io`; the marketing site remains on `ledgerbyte.io`.

## Images and routing

Build `infra/docker/api.Dockerfile` and `infra/docker/web.Dockerfile` from the repository root, one at a time under the repository resource-bound runner. Both pin Node 22 and pnpm 10.15.1, use one build workspace at a time, and run as the unprivileged `node` user. The API image contains production dependencies and the generated Prisma client. The web image contains Next standalone output. Docker build/run validation is still required on a machine with a working Docker daemon; source inspection is not container proof.

An external Docker daemon is outside the Windows runner's process tree. Configure its BuildKit worker/VM with an aggregate 20-GiB memory maximum and at most half the host logical CPUs before building; the CLI runner alone does not enforce the daemon's resources.

`node .do/app-spec.cjs` prints the DigitalOcean App Platform JSON spec. Redirect it to an operator-owned file outside the repository for review. Do not submit the emitted template unchanged: attach the reviewed Frankfurt PostgreSQL cluster and private Spaces bucket, configure secret values in the provider's encrypted runtime settings, and bind a reviewed release revision. Git auto-deployment and autoscaling are disabled. `DIRECT_URL` belongs only in a controlled migration job, never a web/API/worker environment. The `ledgerbyte_runtime` database user must have reviewed limited grants before attachment.

Ingress first preserves `/api/locale` for the existing Next language-switch route. Remaining `/api/*` requests reach the API with `/api` removed; all other paths reach Next. Browser builds use `NEXT_PUBLIC_API_URL=/api`. Thus `/api/auth/login` reaches `/auth/login`, host-only Secure SameSite=Lax cookies work on the same application origin, and the Stripe webhook URL is the same-origin `/api/` prefix plus its controller path. Test language switching, cookie, CSRF, uploaded bodies, download headers, and raw webhook-body handling through the actual ingress before promotion.

## Worker and providers

The API image also runs `node dist/apps/api/src/worker.js`. It boots a minimal Nest application context with no listening HTTP port. It polls sequentially with at most ten tenant visits per tick and one email per tenant by default. It retains the existing database claim/idempotency predicates and rotates the tenant cursor, including after errors. System executions have a nullable audit actor; no user is impersonated. SIGTERM stops new work, lets the current batch drain, disconnects Prisma, and has a 45-second termination deadline.

Email requires both `LEDGERBYTE_EMAIL_RETRY_WORKER_ENABLED=true` and `LEDGERBYTE_EMAIL_RETRY_PROCESSOR_ENABLED=true`; `EMAIL_PROVIDER` remains `smtp-disabled` in the template. Billing uses its separate `LEDGERBYTE_BILLING_WORKER_ENABLED` gate and sequentially reconciles pending webhooks, due lifecycle transitions, and scheduled plan changes. All remain false in committed configuration. Set provider secrets and enable only after the corresponding hosted proof; a running idle worker does not prove delivery. Watch worker heartbeat, failed ticks, oldest pending age, claim age, retry exhaustion, and provider events. One worker process is the default; Redis is not required.

Self-service remains disabled with `LEDGERBYTE_SELF_SERVICE_ENABLED=false`. The exact registered UAE seller and Stripe account match remain unverified; the public LedgerByte brand/contact address cannot fill that gap. Keep `BILLING_SELLER_LEGAL_NAME` blank until verified, then configure it with the two reviewed test price IDs and the payment-method-only portal configuration before hosted billing verification. Billing enforcement and the provider remain `DISABLED`; the current Stripe adapter still rejects live keys. None of these settings belongs in the browser build.

Enabling self-service requires `BILLING_ENFORCEMENT_MODE=ENFORCE`; runtime startup and template preflight reject an enabled registration journey without enforced subscription access.

Storage remains database-backed until the existing S3 adapter passes private Spaces upload/read/hash, wrong-tenant denial, rollback read, and object recovery tests. Then select `s3` for the appropriate provider. Keep API-mediated authorized downloads and signed URLs disabled. Backups need a separately scoped copy and deletion protection; bucket versioning alone is not recovery evidence.

## Verification and promotion

Run the targeted worker Jest suite and `infra/deployment/preflight.test.cjs` through the root resource-bound runner. Run both container builds, import/start smoke, and shutdown tests serially before submitting a spec. Use synthetic isolated hosted data to prove complete accounting/billing/inventory journeys, tenant denial, SMTP delivery and bounce handling, restore, rollback, and capacity at the chosen sizes.

`scripts/saudi-launch-browser-proof.cjs --execute-local-proof` consumes already-built API/web output (web built with `NEXT_PUBLIC_API_URL=/api`) and a fresh migrated disposable local PostgreSQL database from the coordinating native PostgreSQL harness. Run it inside the same bounded job. It binds API, Next, and a same-origin proxy only to loopback, preserves `/api/locale`, launches one Chrome with a two-renderer limit, and starts no worker. Registration, mock-outbox verification, organization setup, and trial selection happen in the browser; authenticated API checks cover a synthetic invoice/PDF, expired-trial write denial with the worker stopped, and revoked-cookie rejection. English/Arabic screenshots and a metadata-only result go to `.dev-logs/saudi-launch-browser-proof`. It refuses ambient environment files, external database targets, non-proof database names, and existing users. It never logs token links, cookies, response bodies, or database URLs; browser requests to other origins are blocked. The parent PostgreSQL harness owns disposal of synthetic database rows.

`node infra/deployment/preflight.cjs --evidence <operator-evidence.json> --revision <40-character-release-sha>` validates fresh evidence references bound to the release. Its contract is `{sourceRevision, checks: {<gate>: {status: "PASS", scope: "hosted-non-production", reference, verifiedAt}}}`. The two human review entries use their actual review scope. Required keys are exported as `gates` in the script. No secret or customer payload belongs in this evidence. A pass says references are complete; it does not independently verify the artifacts or approve production deployment.

Before mutation, create a verified backup, record the previous image digests, application spec, migration head, provider modes, and runtime-secret version references. Apply additive migrations separately with the migration role. Deploy with all provider/worker gates off, verify health/readiness and same-origin auth, then enable only the proved services. Do not automatically apply migrations on container startup.

## Recovery and rollback

Use the managed provider's point-in-time restore to a **new synthetic hosted target**. Do not restore over the source. Quiesce the source so comparison represents the restored snapshot. Reuse the local proof fixture recipe from `apps/api/scripts/local-postgres-drill.ts` in the designated proof environment; that script itself deliberately refuses hosted execution and must retain that boundary.

`apps/api/scripts/verify-hosted-restore.ts` defaults to plan-only. Its explicit `--execute-read-only` mode requires process-only `LEDGERBYTE_DR_SOURCE_DATABASE_URL`, `LEDGERBYTE_DR_RESTORE_DATABASE_URL`, exact `LEDGERBYTE_DR_SOURCE_HOST` and `LEDGERBYTE_DR_RESTORE_HOST`, and both `LEDGERBYTE_DR_SOURCE_QUIESCED=true` and `LEDGERBYTE_DR_SYNTHETIC_SCOPE=true`. Run it with the API workspace's `tsx` through the bounded runner. It enforces TLS, distinct targets, read-only repeatable-read transactions, statement deadlines, and a 10,000-row-per-table synthetic ceiling. It compares selected core table fingerprints and migration history and reuses the established tenant relationship invariant. It prints boolean comparisons only. Its `SELECTED_TABLES_MATCHED` output is explicitly partial and cannot independently satisfy the `databaseRestore` gate: the listed tables omit stock movements/balances/review postings, receipts/issues/returns, command retries, subscriptions/webhooks, session revocations, attachments and other application state. The hosted rehearsal must additionally verify that state and its invariants using the restored synthetic end-to-end fixture before accepting database recovery. The helper never creates a backup, restores, seeds, updates, or deletes. Verify object bytes against archived hashes separately and time the restore; proposed RPO 15 minutes/RTO 4 hours are objectives until a hosted drill measures them.

For an application-only rollback: disable workers/provider execution first, restore the last good image/spec, check `/api/health`, `/api/readiness`, cookie login, tenant denial, and one synthetic document/report read. Preserve database state and outbox claims; never purge/replay them blindly. For an incompatible schema or integrity incident, keep writes paused and follow the existing `docs/production/PRODUCTION_ROLLBACK_RUNBOOK.md`; restore to a new database and review data differences before cutover. Never run automatic destructive down-migrations.

## Budget and current limits

Proposed baseline: web $10, API $12, worker $5, 2-GiB managed PostgreSQL $30.45 plus $6.45 storage reserve, Spaces $5, Resend Pro $20, and two uptime checks net $1: approximately $89.90/month before taxes, domain fees, payment fees, overages, or temporary proof resources. Resend is a pricing candidate; no provider account has been purchased or provisioned by this implementation. Confirm the live provider quote, including independent object backup and retention costs. The worker's 512-MiB size and the API's 1-GiB size are load-test candidates, not capacity guarantees. No HA database standby is included. Set budget alerts at $80/$90 and review growth before exceeding $100; do not delete customer data or stop backups to meet the budget.

Frankfurt is conditional on Saudi transfer/retention and customer-contract review. No claim of Saudi residency, production ZATCA compliance, hosted recovery, live payment collection, or production readiness follows from these files.
